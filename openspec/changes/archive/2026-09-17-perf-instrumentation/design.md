# perf-instrumentation — 设计

## D1：时间线分两段写同一个文件，不做跨语言时间戳传递

Go 与前端是两个进程/两个时钟。传递开始时间戳（让前端算「距进程启动多久」）需要把
Go 的时间点经绑定或事件送给前端，多一条链路、多一处可能失效。

**决策**：两边各自记自己的分段，都写进同一个 `app.log`，靠**绝对时间戳**在阅读时拼起来。
`slog` 的 TextHandler 每行都带 `time=...`，前端日志经 Wails logger 也走同一个 handler，
所以天然按时间排序、可读成一条时间线。

代价：读的人要自己对齐（人眼看，或将来做工具解析）。收益：零新增链路。

## D2：前端必须用 navigation timing，否则量不到最大的一块

Element Plus 的 1.26MB 是在 `main.ts` 执行**之前**被解析执行的（静态 import）。
所以 `performance.now()` 取在 main.ts 顶部**已经错过了**这段——它只会给出「应用级」耗时。

故两段并用：

| 取值 | 覆盖 |
|---|---|
| `performance.getEntriesByType('navigation')[0].domContentLoadedEventEnd` | webview 启动 + 资源加载 + 全部静态 import 的解析执行 |
| `performance.now()` 差值的分段 | 主题 IPC、挂载 |

这样「那 650ms 里 EP 占多少」第一次有了答案——而这正是决定「要不要做按需加载」的前提。

## D3：IPC 采样放在 `invoke()`，但**不**自动猜调用点名字

`invoke()` 是绑定的唯一漏斗，放这里能覆盖全部调用。但它拿到的是闭包
（`() => ListAssets(req)`），拿不到绑定名。

**否决「解析函数源码猜名字」**：`usePagedList` 内部是 `invoke(() => fetcher(req))`，
猜出来会是 `fetcher`——一个误导性的名字比没有名字更糟。

**决策**：`invoke(fn, label?)`，标签可选且显式。`usePagedList` 从 options 透传标签。
没有标签时如实记为「未标注调用」。

## D4：慢查询阈值取 50ms，并排除 ErrRecordNotFound

gorm 默认 `SlowThreshold = 200ms`——对**本地 SQLite** 等于永不触发（索引命中的查询在
微秒级，全表扫一万行也就几毫秒）。200ms 是给远程数据库定的量级。

**决策**：50ms。它高于本地正常查询两个数量级，低于「明显有问题」的查询，
不会产生噪音。

**排除 `ErrRecordNotFound`**：我们的 service 有意用 `apperr.NotFound` 表达「记录不存在」，
gorm 的 ErrRecordNotFound 是这条正常路径的一部分。把它当错误记进日志会让日志充满噪音，
反而埋掉真正的问题。

## D5：不记每次调用，只记超阈值 + 启动期聚合

逐条记 IPC 会让日志量随调用次数线性增长，而绝大多数调用是几毫秒的正常情况——
记下来只是噪音。**决策**：

- 每次调用只在**超阈值**时写一条 warn（这才是要看的）
- 启动期把聚合（次数 / 最大耗时 / 最慢的那个标签）**放进前端启动行**，
  于是每次启动都有一行「IPC 概况」，不随调用量增长

## D6：护栏针对「删掉没有任何症状」的东西

这两类失效没有症状，只能靠检查：

- **gorm logger 未接线** → 慢查询回到 stdout，无人可见（与 Wails logger 同类）
- **启动时间线打点被删** → 优化重新变成盲调，但没有任何报错

故新增护栏：断言 `gorm.Config` 字面量设置了 `Logger`；断言 `main.go` 里的阶段打点
存在且不少于预期数量（解析到 0 个即 Fatal）。

## D7：实跑结果（种子的第一次收成）

启动时间线落地后，三次构建产物实测（macOS arm64，无其他实例预热）：

| 段落 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| Go 组合根（日志/数据库/配置） | 7 ms | 68 ms | — |
| **配置完成 → webview 开始导航** | **2339 ms** | **1358 ms** | **2346 ms** |
| to_js（webview + 资源 + 全部静态依赖含 EP 的解析执行） | 265 ms | 452 ms | 265 ms |
| 主题 IPC / 挂载 | 14 / 19 ms | 5 / 14 ms | — |

**结论与预期相反**：主导成本不是前端包体，而是 Wails 创建 NSWindow/WKWebView 那一段
（1.4–2.3s）。应用侧可控的部分（Go 组合根 + 前端全流程）合计只有 ~300–500ms。

**这也解释了此前的误判**：只有首尾两点时，实测「应用启动 → 前端已挂载」是 359–733ms，
看起来启动很快；但那些样本是在有另一个实例（`wails dev`）预热 WebKit 的情况下取的。
按同样口径重测，无预热时是 **2633ms**——**同一个指标差了 7 倍，而此前无从分辨**。

对「要不要做 Element Plus 按需加载」的影响：包体只影响 to_js 那一段的一部分
（≤265–452ms），相对 2.3s 的窗口创建是次要项；且 to_js 本身的运行间波动就有 1.7×
（265 vs 452），**单次对比无法判断 EP 的真实占比**，需要多次采样或更强的隔离手段。
这正是「先测量」避免的那类无用功。

## D8：实跑发现的第二个问题（已修）

首次实跑时启动行的 `ipc_calls=0`，但 `theme_ms=15` 明明有一次往返——原因是
`stores/app.ts` 的 `GetTheme`/`SetTheme` **直接调绑定，绕过了 `invoke()` 这个唯一漏斗**，
所以没进 IPC 统计。同时发现 `SetTheme` 的错误只 `console.error`——而打包后的应用没有
DevTools，那条错误等于没记（与本变更要解决的「日志写到无人可见的地方」是同一类）。

已改为经 `invoke(fn, label)` 调用：进统计、带标签，错误经 `logError` 落到 `app.log`。
